## 1. 프로그래밍 오류 종류

프로그래밍의 오류(error)란 프로그램이 개발자가 의도하지 않은 상태로 빠지는 것. 오류 크기에 따라 영향 범위가 달라지며, 최악의 경우 프로그램이 강제 종료됨. 에러 처리를 통해 의도치 않은 상태로 빠지지 않게 할 수 있음.

| 종류 | 발생 시점 | 설명 |
|---|---|---|
| **컴파일 에러** | 컴파일 시 | 문법 오류 등. IDE가 `javac`로 주기적으로 컴파일해 미리 표시. 실행 전에 발생하므로 가장 안전한 에러 |
| **런타임 에러** | 프로그램 실행 시 | 개발자의 설계 미스에서 발생. 발생 시 원인 분석(Root Cause Analysis)으로 해결 필요. 100% 피하기 어려움 |
| **논리 에러** | 실행 시 | 프로그램은 정상 실행되지만 의도와 다르게 동작 (= 버그) |

## 2. Java의 오류와 예외

자바는 크게 2가지의 오류 클래스를 제공함.

- **`Error`**: 개발자가 다룰 수 없는 오류. 프로그램이 무조건 종료됨. `OutOfMemoryError` 같은 심각한 시스템 오류로 예외 처리 불가
- **`Exception`**: 개발자가 다룰 수 있는 오류. 잡아서 안전하게 종료, 무시, 또는 정상 작동으로 복구할 수 있음. 컴파일 타임 에러와 런타임 에러를 모두 포함

### 2.1 Checked Exception vs Unchecked Exception

| 구분 | Checked Exception | Unchecked Exception |
|---|---|---|
| 관련 에러 | 컴파일 타임 | 런타임 |
| 처리 여부 | **반드시 예외 처리 필요** (`try-catch` 또는 `throws`) | 명시적으로 처리 안 해도 됨 |
| 미처리 시 | 컴파일 에러 | 컴파일 통과 |
| 확인 시점 | 컴파일 시 | 런타임 |

이 둘로 나누는 핵심 기준은 컴파일/런타임 여부보다 **예외 처리 코드의 필수 여부**.

## 3. 예외 처리 방법

2가지 방법이 있음.

1. **`try-catch` 문**: 예외를 직접 처리
2. **`throws` 키워드**: 호출자에게 예외 처리를 위임

> 단, 코드로 모든 예외를 처리한다고 해서 100% 안전이 보장되지는 않음.

예외 처리의 핵심은 프로그램이 내부적으로 비정상 상태에 빠졌을 때 정상 상태로 돌아오게 하는 것.

### 3.1 Resource 처리

- **Resource**: Java가 외부에서 가져오는 값들 (DB, Network, File 등). 자바 내부 코드와 달리 불안정함
- Resource를 호출했다면 **반드시 `close()`** 해주어야 함

### 3.2 finally / try-with-resources

- **`finally {}`**: `try-catch`에서 예외 발생 여부와 관계없이 `{}` 안의 코드를 실행
- **`try-with-resources`**: `close()`로 인한 코드 복잡성을 줄이기 위해 도입

```java
try (FileWriter f = new FileWriter("data.txt")) {
    f.write(...);
} catch (IOException e) {
    // ...
}
```

`try`의 `()` 안에 Resource 작업을 적으면 자동으로 `close()`가 호출됨.

## 4. 예외 기본 규칙

- 예외는 **잡거나(처리)** 또는 **던져야 함** (폭탄 돌리기와 비슷)
  - "던진다" = 상위 클래스(호출자)로 예외 처리를 위임
- 예외를 잡거나 던질 때, **지정한 예외뿐 아니라 그 자식 예외도 모두 처리됨**
  - 예: `Exception`으로 잡으면 `IOException` 등 하위 계층을 모두 잡음
- `Exception`과 그 하위 예외는 모두 컴파일러가 체크하는 **체크 예외** (단, `RuntimeException`은 예외)
- 체크 예외는 **잡아서 처리하거나 밖으로 던지도록 선언**해야 함. 그렇지 않으면 컴파일 오류

## 5. 체크 예외 활용

- **기본적으로 언체크(런타임) 예외를 사용하는 게 좋음**
- 체크 예외는 **비즈니스 로직상 의도적으로 던지는 예외에만 사용**
  - 반드시 처리해야 하는 문제일 때만 체크 예외 사용
  - 예: 계좌 이체 실패 예외, 결제 시 포인트 부족 예외, 로그인 ID/PW 불일치 예외

### 5.1 체크 예외의 문제점

- `Repository`는 DB에 데이터를 저장·관리하면서 `SQLException` 체크 예외를 던짐
- `NetworkClient`는 외부 네트워크에 접속하며 `ConnectionException` 체크 예외를 던짐
- 서비스 계층은 두 예외를 모두 처리해야 하지만, 연결 실패나 DB 문제는 애플리케이션 로직에서 처리할 방법이 없으므로 그대로 밖으로 던짐
- 컨트롤러 역시 처리할 방법이 없음. 이런 **해결 불가능한 공통 예외**는 별도의 오류 로그를 남기고 개발자가 빨리 인지할 수 있도록 알려야 함

문제

- 대부분의 예외는 복구가 불가능. 일관성 있는 공통 처리가 필요함 (`@ControllerAdvice` 활용)
- 복구 불가능한 예외인데도 체크 예외라서 `throws`로 계속 던져야 함. 향후 Repository를 변경하면 `SQLException` → `JPAException` 식으로 모두 수정해야 함

### 5.2 해결법

체크 예외를 `try-catch`로 잡아 **언체크 예외(`RuntimeException`)로 전환**해 던짐. 이때 **기존 예외를 함께 포함**해야 스택 트레이스에서 원인을 추적할 수 있음.

### 5.3 예외 포함과 스택 트레이스

> 예외 전환 시 기존 예외를 포함하지 않으면 큰 문제가 발생함.

- 로그 출력 시 마지막 파라미터에 예외를 넣으면 스택 트레이스가 함께 출력됨

```java
log.info("message={}", "message", ex);
```

마지막 `ex`를 전달하면 스택 트레이스가 로그에 출력됨.
