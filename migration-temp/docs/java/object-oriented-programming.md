## 1. 클래스 (Class)

- 객체를 프로그램 상에서 사용하기 위해 기술해 놓은 **설계도**
- 추상화 작업을 통해 추출한 객체의 특징을 **필드**와 **메서드**로 분류
- 객체 생성을 위해서는 반드시 상응하는 클래스가 필요. `new` 연산자 + 클래스의 생성자 호출로 객체 생성
- Java에서 클래스는 가장 기본적인 코드 작성 단위. 모든 코드는 클래스 내에 작성

## 2. 메서드 (Method)

### 2.1 함수 (Function)

- 특정 작업을 수행하는 명령(코드)들의 단일 집합
- 변수와 달리 **호출(call, 실행)이 가능**. 함수 이름과 괄호로 호출
- 코드의 구조화: 반복되는 코드를 별도 함수로 묶어 호출 코드로 대체하면 전체 코드가 간결해짐
- 단, 반복된다고 무조건 함수로 묶는 게 좋은 것은 아님

### 2.2 메서드의 정의

- **객체에 귀속된 함수**. 객체의 동사적 요소를 코드로 표현할 때 사용
- 일반 함수와 달리, 귀속된 객체의 명사적 요소(필드)에 접근 가능
- "객체에 붙어 있는 함수"

### 2.3 메서드의 특징

- **input**: 매개변수, **output**: 리턴값
  - 매개변수는 `parameter`, 매개변수에 담긴 값은 `argument`
- `static`이 명시되지 않은 메서드는 객체가 `new` + 생성자로 생성되지 않으면 사용 불가
- 외부(다른 메서드 안)에서 메서드를 사용하는 행위는 **메서드 호출**. 메서드 입장에서는 "호출되었다"고 표현
- 접근 제한자를 설정하지 않으면 **상속의 대상**이 됨
- `final` 키워드를 사용하면 **오버라이딩 불가**
- `main` 메서드는 특수 함수. Java 프로그램 실행 시 가장 먼저 실행됨. 공식적인 프로그램 시작점
- `static` 메서드: 동일 클래스 내에서 `static`이 아닌 일반 메서드를 호출할 수 없음
- **생성자**: `new`로 객체 생성 시 반드시 호출되는 메서드
  - 객체 생성 시 한 번만 호출. 이후 다른 메서드에서 호출 불가
  - 메서드이므로 **오버로딩은 가능**, 클래스 상속 시 **오버라이딩은 불가**
  - 상위 클래스의 생성자 호출 시 `super` 키워드 사용
  - 다른 생성자를 `this()`로 호출할 수 있음. 단, **본문의 가장 첫 줄**에 위치해야 함
  - 생성자 간 순환 호출 금지 (무한 호출 발생)

## 3. 객체 지향 프로그래밍

- **객체**: 우리가 표현할 수 있는 실제 세계의 모든 사물
- **개념적 객체**: 명확한 실체가 아니라 사람의 지식에 의한 객체
- **물리적 객체**: 실제 존재하는 객체

객체 지향 프로그래밍은 현실 세계에서 객체 간 상호작용을 프로그래밍 방법론으로 체계화한 것. 코드를 데이터와 동작이 캡슐화된 독립적인 모듈 단위(객체)로 구성하고, 코드 재사용성과 유연성을 높이며 실제 개체를 모델링하는 패러다임.

프로그래밍 관점에서 객체의 두 가지 요소

- **필드**: 내부적으로 가지고 있는 데이터
- **메서드**: 행위

## 4. 객체 지향의 4가지 특징

### 4.1 추상화 (Abstraction)

- 특정 객체를 우리가 구상하는 도메인(세계관) 속에서 일반화(generalize)하는 과정
- 도메인에 필요한 객체의 속성/행위(필드, 메서드)는 남기고, 불필요한 것은 제거
- 필요시 속성/행위를 추가 가능

### 4.2 은닉화 (Encapsulation)

- 객체 내부의 속성을 외부로부터 숨기는 과정
- **왜 숨기는가?** 설계자가 의도한 대로 객체를 사용하게 하기 위함. 모든 속성이 외부에서 접근 가능하면 의도와 다르게 변경될 수 있음
- 접근 가능한 속성과 불가능한 속성으로 접근을 제어함

### 4.3 상속 (Inheritance)

- 클래스 간 관계가 존재하며, 상위/하위 클래스로 나뉨
- 상위 = 부모 클래스, 하위 = 자식 클래스
- 자식 클래스는 부모 클래스의 필드/메서드를 동일하게 물려받음 (= 상속)
- 자식 객체 생성 시 **부모 객체가 먼저 생성됨**
- 은닉화로 접근이 제한된 속성에 상속을 적용하기 위해 `protected` 접근 제한이 추가됨

### 4.4 다형성 (Polymorphism)

- 한 객체가 여러 타입의 객체로 취급될 수 있는 능력
- **역할과 구현**으로 세상을 구분해 각 역할(인터페이스)만 주어지면, 유연성과 변경 용이성을 확보 가능

**역할과 구현의 분리**

- 역할과 구현으로 구분하면 세상이 단순·유연해지고 변경이 편리
- 장점
  - 클라이언트는 대상의 **역할(인터페이스)만 알면 됨**
  - 구현 대상의 내부 구조를 몰라도, 변경되어도 영향을 받지 않음
  - 구현 대상 자체를 변경해도 영향을 받지 않음
- 자바 언어의 다형성으로 활용
- **역할 = 인터페이스**, **구현 = 인터페이스를 구현한 클래스/구현 객체**
- 객체 설계 시 역할(인터페이스)을 먼저 부여하고, 그 역할을 수행하는 구현 객체를 만듦
- 클라이언트(요청) ↔ 서버(응답). 수많은 객체가 협력 관계를 가짐

**자바 언어의 다형성 활용**

- 오버라이딩으로 인터페이스 구현 객체를 실행 시점에 유연하게 교체 가능
- 클래스 상속 관계도 다형성/오버라이딩 적용 가능

**다형성의 본질**

- 인터페이스를 구현한 객체 인스턴스를 실행 시점에 유연하게 변경 가능
- 본질을 이해하려면 객체 사이의 **협력**이라는 관계에서 시작해야 함
- 클라이언트를 변경하지 않고 서버 구현을 유연하게 변경할 수 있음

## 5. SOLID — 객체 지향 설계 5원칙

| 원칙 | 약어 | 정의 |
|---|---|---|
| **단일 책임 원칙** | SRP (Single Responsibility) | 한 클래스는 하나의 책임만 가져야 함 |
| **개방-폐쇄 원칙** | OCP (Open/Closed) | 소프트웨어 요소는 확장에 열려 있고 변경에 닫혀 있어야 함 |
| **리스코프 치환 원칙** | LSP (Liskov Substitution) | 프로그램의 객체는 정확성을 깨지 않으면서 하위 타입의 인스턴스로 바꿀 수 있어야 함 |
| **인터페이스 분리 원칙** | ISP (Interface Segregation) | 범용 인터페이스 하나보다, 특정 클라이언트용 인터페이스 여러 개가 낫다 |
| **의존관계 역전 원칙** | DIP (Dependency Inversion) | 추상화에 의존하고, 구체화에는 의존하지 않는다 |
