## 1. 인터넷 네트워크

- **인터넷 통신**: 클라이언트와 서버가 메시지를 주고받으며 통신함. 인터넷 망은 복잡하게 구성되어 있어, 메시지는 중간 노드들을 거쳐 서버로 전달됨
- **IP**: 클라이언트와 서버가 통신하려면 정확한 주소가 필요함. 인터넷상의 주소를 IP라 하며, 지정된 IP 주소로 데이터를 전달함
  - 패킷: 통신 단위. 데이터는 패킷 단위로 전달
  - 패킷 정보: 출발 IP, 도착 IP, 전송 데이터 등을 포함
  - 클라이언트가 패킷을 서버에 전달하면, 서버도 패킷으로 응답
- **IP 프로토콜의 한계**
  - 비연결성: 받을 대상이 없거나(소실), 서비스가 불능 상태여도 패킷은 전송됨
  - 비신뢰성: 중간에 패킷이 사라지거나 순서대로 도착하지 않을 수 있음
  - 프로그램 구분 불가: 같은 IP에서 여러 애플리케이션이 통신할 때, 어느 프로그램에 패킷을 전달할지 모호함

### 1.1 TCP / UDP

인터넷 프로토콜 스택의 4계층 구조임.

![인터넷 프로토콜 4계층 구조](images/http-01.webp)

| 계층 | 대표 프로토콜 |
|---|---|
| 애플리케이션 계층 | HTTP, FTP |
| 전송 계층 | TCP, UDP |
| 인터넷 계층 | IP |
| 네트워크 인터페이스 계층 | (이더넷 등) |

**TCP** (Transmission Control Protocol, 전송 제어 프로토콜)
- 연결 지향: TCP 3-way handshake로 가상 연결을 맺음
  1. SYN(접속 요청): 클라이언트가 접속을 요청
  2. SYN+ACK(요청 수락): 서버가 요청을 수락하고 접속을 요청
  3. ACK: 클라이언트가 수락을 확인. 이 단계에서 데이터 전송도 함께 가능
- 데이터 전달 보증: 수신 확인이 오기 때문에 전달이 보증됨
- 순서 보장: 패킷이 순서대로 전송되며, 순서가 어긋나면 재요청
- 신뢰할 수 있는 프로토콜이며, 현재 대부분의 통신에서 TCP 사용

**UDP** (User Datagram Protocol, 사용자 데이터그램 프로토콜)
- 기능이 거의 없음
- TCP 3-way handshake 없음
- 데이터 전달 보증 없음
- 순서 보장 없음
- 대신 단순하고 빠름
- IP와 비슷하며, PORT와 체크섬 정도만 추가
- 신뢰성이 필요하면 애플리케이션에서 추가로 처리해야 함

### 1.2 PORT

한 호스트에서 둘 이상의 연결이 필요할 때 PORT 번호로 프로세스를 구분함.

- 할당 가능 범위: 0 ~ 65535
- Well-known port: 0 ~ 1023 (직접 사용하지 않는 것이 좋음)
  - FTP: 20, 21
  - HTTP: 80
  - HTTPS: 443

### 1.3 DNS

DNS(Domain Name System)는 IP가 변경 가능하고 기억하기 어려운 숫자 조합인 문제를 해결하기 위해 만들어진 시스템.

- 도메인 명을 IP 주소로 변환 (전화번호부와 같은 역할)
- 흐름: 클라이언트가 도메인 명으로 요청 → DNS 서버가 IP 주소를 응답 → 클라이언트가 해당 IP로 접속

## 2. URI와 웹 브라우저 요청 흐름

### 2.1 URI

URI(Uniform Resource Identifier)는 다음 의미로 구성됨.

- Uniform: 리소스를 식별하는 통일된 방식
- Resource: URI로 식별할 수 있는 모든 자원 (제한 없음)
- Identifier: 다른 항목과 구분하는 데 필요한 정보

![URI, URL, URN의 관계](images/http-02.webp)

- URL(Locator): 리소스의 위치를 지정
- URN(Name): 리소스에 이름을 부여
- 위치는 변할 수 있지만 이름은 변하지 않음
- URN 이름만으로 실제 리소스를 찾는 방법은 보편화되지 않음

### 2.2 URL 전체 문법

```
scheme://[userinfo@]host[:port][/path][?query][#fragment]
```

| 요소 | 설명 |
|---|---|
| `scheme` | 사용할 프로토콜 (http, https 등). 자원 접근 방식 약속 |
| `[userinfo@]` | URL에 사용자 정보 포함하여 인증. 거의 사용하지 않음 |
| `host` | 호스트명. 도메인 명 또는 IP 주소를 직접 사용 가능 |
| `[:port]` | 접속 포트. 일반적으로 생략 (http는 80, https는 443) |
| `[/path]` | 리소스 경로. 계층적 구조 |
| `[?query]` | `key=value` 형태. `?`로 시작, `&`로 추가. 웹 서버에 전달하는 파라미터(문자) |
| `[#fragment]` | HTML 내부 북마크 등에 사용. 서버에 전송되지 않음 |

### 2.3 웹 브라우저 요청 흐름

URL을 처음 접속할 때:

1. DNS를 조회해 IP 주소를 받고, HTTP 요청 메시지를 생성
2. Socket 라이브러리를 통해 전달
3. TCP/IP 패킷을 생성. 전송 데이터로 HTTP 메시지가 포함됨
4. 서버가 HTTP 응답 메시지를 응답 패킷으로 보냄

![HTTP 요청·응답 패킷 흐름](images/http-03.webp)

## 3. HTTP

HTTP(HyperText Transfer Protocol)는 HTML, 텍스트, 이미지, 음성, 영상, 파일 등 거의 모든 데이터를 메시지에 담아 전송 가능. 서버 간 데이터 교환에서도 대부분 HTTP 사용.

### 3.1 HTTP 특징

- **클라이언트-서버 구조**: Request/Response 구조. 클라이언트가 요청을 보내고 응답을 대기하면, 서버가 결과를 만들어 응답함
- **무상태 프로토콜 (Stateless)**
  - 서버가 클라이언트 상태를 보존하지 않음 (예: 이전 로그인 상태가 유지되지 않음)
  - 서버 확장성은 높지만 (서버가 여러 대일 때 장애 대응이 쉬움), 클라이언트가 필요한 데이터를 매 요청마다 보내야 함 (예: 로그인 정보 반복 전송)
- **비연결성 (Connectionless)**
  - 기본적으로 연결을 유지하지 않아 서버 자원을 효율적으로 사용
  - 매 요청마다 TCP/IP 연결을 새로 맺어야 함 (3-way handshake)
  - 웹 페이지 하나에 JS, CSS 등 수많은 자원이 포함되므로 비용이 큼
  - HTTP **지속 연결**(Keep-Alive)로 이 문제를 완화

### 3.2 HTTP 메시지

모든 데이터를 HTTP 메시지에 담아 주고받음.

![HTTP 메시지 구조](images/http-04.webp)

#### 요청 메시지

- `start-line`: request-line
- `request-line`: `method SP request-target SP HTTP-version CRLF`
- 경로는 `/`로 시작하는 절대 경로
- HTTP 버전: 보통 `HTTP/1.1`

**HTTP 메서드** — 서버가 수행할 동작을 지정함.

| 메서드 | 동작 |
|---|---|
| GET | 리소스 조회 |
| POST | 요청 데이터 처리. 메시지 바디로 데이터 전달 |
| PUT | 리소스 대체. 없으면 생성 |
| PATCH | 리소스 부분 변경 |
| DELETE | 리소스 삭제 |

#### 응답 메시지

- `start-line` = `status-line`
- `status-line`: `HTTP-version SP status-code SP reason-phrase CRLF`

**HTTP 상태 코드** (대표)

| 코드 | 의미 |
|---|---|
| 200 | 성공 |
| 400 | 클라이언트 요청 오류 |
| 500 | 서버 내부 오류 |

#### HTTP 헤더

- HTTP 전송에 필요한 부가 정보가 모두 담김
- 예: 메시지 바디의 내용·크기, 압축, 인증, 클라이언트/서버 애플리케이션 정보, 캐시 관리 정보 등
- 표준 헤더가 다양하게 정의되어 있음

#### HTTP 메시지 바디

실제 전송할 데이터(HTML, 이미지, 영상, JSON 등)가 담기며, 형식 제한 없이 모든 데이터 전송 가능.
