## 1. AWS Lambda 개요

- 서버를 프로비저닝하거나 관리할 필요 없이 코드를 실행할 수 있는 **서버리스 컴퓨팅 서비스**
- 고가용성 인프라에서 코드를 실행. 서버/OS 유지 관리, 용량 프로비저닝 및 자동 조정, 코드/보안 패치 배포, 로깅 등 모든 컴퓨팅 리소스 관리를 AWS가 수행
- 사용자는 코드만 제공하면 됨. 사용한 컴퓨팅 시간만큼만 비용 지불

## 2. Lambda 사용 시나리오

- 빠르게 스케일 업하고, 수요가 없을 때 0으로 스케일 다운하는 시나리오에 이상적
- 사용 예시
  - **S3 트리거**: S3 이벤트로 Lambda를 실시간 트리거해 데이터 처리
  - **Amazon Kinesis 연계**: 앱 작업 추적, 거래 주문 처리, 데이터 정리 등 실시간 스트리밍 처리
  - **자동 스케일 웹 앱**: 다른 AWS 서비스와 결합해 여러 데이터 센터에서 고가용성 구성으로 자동 스케일 업/다운
  - **서버리스 백엔드**: IoT 및 서드파티 API 요청 처리
  - **API Gateway 연계**: 백엔드를 구축해 API 요청 인증·처리

## 3. 주요 용어

- **Lambda 함수**: 애플리케이션을 빌드하는 데 사용하는 Lambda의 기본 구성 요소
  - 사용자가 버튼을 클릭하거나 S3 버킷에 파일을 업로드하는 것 같은 이벤트에 응답해 실행되는 코드
  - 일종의 독립적인 프로그램. 하나의 특정 작업/목적을 가지며, 필요할 때만 실행되고 완료되면 자동 중지
  - 함수가 실행되면 Lambda는 **핸들러 함수**를 실행. 이벤트 데이터가 핸들러에 직접 전달됨
  - 코드에 둘 이상의 메서드/함수를 포함할 수 있지만, **핸들러는 하나만** 가질 수 있음
- **Lambda 런타임**: 함수가 실행되는 언어별 환경
  - 안전하고 격리된 실행 환경에서 실행. 필요한 프로세스와 리소스를 관리
  - 언어별로 여러 런타임 환경 제공
- **트리거 / 이벤트 소스 매핑**: 특정 이벤트가 발생할 때 다른 AWS 서비스에서 함수를 간접 호출하는 방법
  - 일반적으로 API 호출보다 트리거를 통한 호출 사용
  - 특정 트리거 기반으로 람다 함수를 간접 호출함

  ![Lambda 트리거 예시: S3 이벤트로 함수 호출](images/aws-lambda-01.webp)

  - 예: S3 버킷에 객체가 추가될 때마다 함수가 실행되고, CloudWatch Logs에 객체 유형을 출력
- **이벤트 객체**: 함수가 처리할 이벤트 데이터가 포함된 JSON 객체
- **Lambda 권한**: 함수가 상호 작용할 수 있는 다른 AWS 서비스, 그리고 함수에 접근할 수 있는 사용자를 제어하는 방법

## 4. 이벤트 및 이벤트 기반 아키텍처

- 폴링/웹훅을 이벤트로 대체할 수 있음
  - **폴링**: 데이터 요청이 있는지 지속적으로 확인하는 방식
  - **웹훅**: 이벤트가 발생했음을 서버에서 클라이언트로 전송하는 방식
  - 두 방식 모두 Downstream 서비스와의 동기화에 지연이 있어 업데이트 가져오기에 비효율적
- 이벤트 방식으로 대체하면 CPU 사용률과 잠재 비용이 감소함

## 5. Lambda 안티패턴

### 5.1 Lambda 모놀리스

- 기존 서버나 EC2 인스턴스에서 오는 많은 API Gateway 요청을 **단일 Lambda 함수**가 모두 처리하게 만드는 방식
- 문제점
  - 함수 패키지가 매우 큼
  - 권한 부여 문제로 보안 취약
  - 코드 리포지토리 자체가 거대해 유지 관리 어려움

![Lambda 모놀리스 구조](images/aws-lambda-02.webp)

### 5.2 재귀 패턴

- 람다 함수가 다른 이벤트를 호출하고, 그 이벤트가 다시 람다 함수를 호출하는 패턴
- 무한 루프가 발생할 수 있어 반드시 피해야 함

![재귀 패턴](images/aws-lambda-03.webp)

### 5.3 단일 람다 함수 내 동기식 대기

- 단일 람다 함수에서 다른 응답을 동기식으로 기다리는 패턴
- 순차적 활동으로 대기 시간이 누적되어 실행 시간이 늘어나고 비용 증가

![단일 함수 내 동기식 대기](images/aws-lambda-04.webp)

- **실제 사례** (프로젝트 당시 직접 설계한 방식): Lambda 함수가 DB에서 데이터를 조회한 뒤, 데이터가 없으면 S3 버킷의 파일을 제거하는 동작
  - DB 조회 후 S3 삭제가 동기식으로 일어나 좋지 않은 설계가 됨
  - 람다 함수에는 시간 제한(최대 15분)도 있음
- **해결 방법**
  - 람다 함수를 쪼개 각 함수가 하나의 데이터에만 접근하도록 분리

  ![분리된 람다 함수 구조](images/aws-lambda-05.webp)

  - 비용 측면을 고려해 비동기식으로 전환
