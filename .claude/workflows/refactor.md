# 워크플로우: 리팩토링

> 트리거: "X 리팩토링해줘", "Y 정리해줘"

## 목적
기능은 유지하면서 코드 품질을 개선하는 안전한 리팩토링.

## 핵심 원칙

### 1. 안전 우선
- **기능 변경 절대 금지** (외부 동작 동일하게)
- 작은 단위로 나눠서 진행
- 각 단계마다 검증

### 2. 테스트가 안전망
- 리팩토링 전 테스트 존재 확인
- 없으면 먼저 테스트 작성
- 리팩토링 후 모든 테스트 통과

### 3. 점진적 개선
- 한번에 모든 걸 바꾸지 않음
- 작은 PR 여러 개가 더 안전

## 흐름도

```
[리팩토링 대상 파악]
       ↓
[기존 테스트 확인]
       ↓ (없으면)
test-writer (특성 테스트 먼저 작성)
       ↓
Explore (영향 범위 분석)
       ↓
[리팩토링 계획 수립]
       ↓
[작은 단위로 변경]
       ↓
빌드 + 테스트 통과 확인
       ↓
┌──────┴──────┐
↓             ↓
code-rev    sec-aud      (병렬 검증)
└──────┬──────┘
       ↓
docs-writer (변경 사항 문서화)
       ↓
[리팩토링 완료]
```

## 리팩토링 유형별 가이드

### 1. 컴포넌트 분리
- **목표**: 큰 컴포넌트를 작은 단위로
- **체크**: 단일 책임 원칙
- **에이전트**: ui-designer + code-reviewer

### 2. 중복 코드 제거
- **목표**: DRY 원칙 적용
- **체크**: 진짜 중복인지, 우연한 일치인지
- **에이전트**: code-reviewer + Explore

### 3. 타입 강화
- **목표**: any 제거, 정확한 타입
- **체크**: 런타임 동작 동일
- **에이전트**: code-reviewer

### 4. 폴더 구조 개선
- **목표**: 직관적인 위치로 이동
- **체크**: import 경로 모두 갱신
- **에이전트**: code-reviewer + docs-writer

### 5. DB 스키마 개선
- **목표**: 정규화/비정규화 최적화
- **체크**: 마이그레이션 안전성
- **에이전트**: db-architect + security-auditor

## 단계별 체크리스트

### 사전
- [ ] 리팩토링 대상 파악
- [ ] 기존 테스트 존재 확인
- [ ] 기존 테스트 통과 확인
- [ ] 영향 범위 분석

### 진행
- [ ] 작은 단위로 변경
- [ ] 각 단계 후 빌드 확인
- [ ] 각 단계 후 테스트 실행

### 사후
- [ ] code-reviewer 검증
- [ ] security-auditor 검증 (보안 관련 시)
- [ ] 모든 테스트 통과
- [ ] **docs/system/* 동기화** (구조 변경 시 overview/pages/components/data-flow/integrations 중 해당 파일)
- [ ] 기존 문서 갱신 (architecture, conventions)
- [ ] 변경 이유 명확히 (커밋 메시지)

## 위험 신호 (즉시 중단)

- 테스트가 깨지기 시작
- 빌드 실패 빈도 증가
- 변경 범위가 예상보다 커짐
- 기능 동작 변경 발견

→ 즉시 변경 사항 되돌리고 사용자와 재검토
